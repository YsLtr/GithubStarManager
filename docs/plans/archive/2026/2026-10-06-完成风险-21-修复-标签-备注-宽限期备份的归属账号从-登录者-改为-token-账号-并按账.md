# 完成风险 21 修复：标签 / 备注 / 宽限期备份的归属账号 = token 账号

> 状态：待审查（deep-plan P4，第 3 版 —— 按用户 2026-10-06 裁定与本日实测修订）
> 目标版本：4.18.0
> 用户口径原文（2026-10-05）：「备份应当也有所属标记，归属到某一用户下 … tag/备注应当只跟 token 账号走。
> 用户忽略警告就已知晓此时内容不属于此登录账户而是属于 token 所属账户。」
> 用户 2026-10-06 追加裁定：**不新增任何 UI**（不做归属 chip）；既有归属横幅要同时显示 token 账号与
> 网页登录账号、表明差异，并在 token 变化或网页登录变化时重新弹出；**归属 id 不做会话级冻结**，改为
> 「保存 token 时即确认该 token 对应用户 id」；零权限 fine-grained PAT 能否调 `GET /user` **必须实测**
> —— **已实测：可用**（见 §2.1，推翻了本方案第 2 版的 worst-case 设计）。
> 共识前提（D30）：**开发阶段、不存在任何已有用户** ⇒ 免迁移代码成立；该前提一旦失效，本方案的迁移结论立即作废。

---

## 1. 一句话方案

把「标签 / 备注 / 宽限期备份」的存储命名空间从**页面登录者**（`octolytics-actor-id`）改为
**token 账号**（`GET /user` 的 `id`，以**凭证指纹**为键持久化在既有的 `stars_account_identity` 缓存里，
**在保存 token 时就写入**；读路径同步查表、查不到才回退登录者）；宽限期备份（原 `stars_pending_delete`，
单份全局键）改为**按键分区** `stars_pending_delete_<归属id>`；披露**全部由既有的归属横幅承担**
（显示 token 账号与网页登录账号两者 + 归属说明 + 任一侧变化即重弹），**不新增任何 UI 节点**。

理由一句话：屏幕上的列表由 `GET /user/starred`（带 token）决定 ⇒ **展示与归属必须同账号**，
否则屏幕上是 A 的列表、标签却记在 B 名下 —— 那正是风险 21 的形状。

外部事实结论 = **Adopt**：GitHub 官方明文「PAT 即你的身份」直读实现（`.pi/tmp/risk21-research.md` 的 Verdict 行）；
其中唯一无官方依据的一项（零权限 fine-grained PAT 调 `GET /user`）已由**真机实测确认可用**（§2.1）。

### 2.1 外部事实（联网查证 + 真机实测，证据全文见 `.pi/tmp/risk21-research.md`）

| 事实 | 强度 | 结论 |
|---|---|---|
| 带 PAT 调 `GET /user/starred` 返回的是 **token 账号**的列表 | 官方明文 | 端点页「Lists repositories the **authenticated user** has starred」+「Personal access tokens **act as your identity** … when you make requests to the REST API」⇒ 屏幕上的列表就是 token 账号的 |
| 带 PAT 调 `GET /user` 返回 **token 账号** | 官方明文 | 同上；官方 `gh` 仓库文档用 `gh api /user \| jq .login` 随 `gh auth switch` 变化证明「身份跟着**生效 token** 走」 |
| PAT 所属账号可用 `GET /user` 的 `id` 自证 | 官方明文 | `GET /user/{account_id}`「takes their **durable user ID** instead of their login, **which can change over time**」⇒ 用**数字 id** 当比对键正确（与 ADR 0007 一致），login 只作展示 |
| 零权限 fine-grained PAT 能否调 `GET /user` | **已实测可用** | 官方两张权限表**都不收录**该端点、端点页无 fine-grained 字样（同一清单连 `GET /rate_limit` / `GET /meta` 这类免权限端点也漏 ⇒ 它是「权限映射清单」不是「可调用全集」）。**用户 2026-10-06 真机实测：零权限 fine-grained PAT 调 `GET /user` 返回 200 且带 `id`** ⇒ 不再按 worst case 设计，绑定路径（§3.2）对两类凭证都成立。遗留：`docs/adr/0007:45` 声称此处有「官方端点页原文」，本次联网复核**未能复现**该引文 ⇒ 该 ADR 的**依据**改为实测（T7 落盘），结论不变 |
| 仅靠会话 Cookie 打网页 `POST /{o}/{r}/star` | 无官方文档 | 社区实现一致证明靠会话 CSRF/nonce、未登录表单根本不渲染 ⇒ 动作记在**会话登录者**名下，但无契约（本仓库同向证据见 `docs/research-web-star-endpoints.md`） |
| token 账号 ≠ 浏览器登录者是**官方承认的常态** | 官方明文 | 多账号可同时存在于浏览器；`gh` 官方文档记录真实事故「received credentials for wilmartin_microsoft, **did you use the correct account in the browser?**」；`GH_TOKEN` 官方说明其优先于已存凭证 |
| 读通道与写通道**身份可能不同**（镜像错配） | 官方（读）/ 无文档（网页写） | classic 写 ⇒ token 账号；fine-grained 与网页回落 ⇒ 会话登录者 ⇒ **UI 文案不得声称「读写永远同账号」**（§3.5 守住这条） |

## 3. 设计

### 3.1 归属身份模块（新增叶子模块）

新增 `src/storage/accountIdentity.ts`，**只依赖 `constants` / `gm` / `tokenConfig`**：

```
fingerprint(tok)                           // 从 accountGuard.ts 原样搬来（FNV-1a，32 位）
getTokenIdentitySync(tok)                  // 按指纹查 STORAGE_KEYS.accountIdentity；纯同步、零网络、零写入
rememberTokenIdentity(tok, identity)       // 写同一张缓存
resolveTokenIdentity(tok)                  // 把 accountGuard 的 GET /user 网络函数搬来：
                                           //   200 ⇒ 写缓存并返回身份；401 ⇒ 走既有 notifyTokenIssue 并返回 null
                                           //   其余（403/5xx/429/网络）⇒ 返回 null（**不写缓存**，留给下次重试）
setTokenVerified(raw)                      // 见 §3.2
```

`src/accountGuard.ts` 改为 import 这些函数并删掉本地副本（`fingerprint` / `fetchTokenIdentity` / 缓存读写各一处），
判定矩阵、文案、窄视口门**一行不动**。依赖方向单向（`accountIdentity → tokenConfig`），无导入环。

> 为什么不直接让 `storage/tags.ts` import `accountGuard`：scout 已证明现状不成环（`accountGuard` 闭包无 storage 模块），
> 但那会让存储层依赖「网络请求 + token 失效上报」模块，并把 `starWrites` / `boot` / `utils` 拖进
> `tests/exportImport` 的依赖闭包。叶子模块更小、更稳，也让「token 身份」只有一处实现。

### 3.2 保存 token 时即绑定身份（本版的核心改动）

`setTokenVerified(raw)` 是 token 的**唯一写入点**（今天的两处直接 `gmSet` 合并过来）：

```
raw 为空        ⇒ 清除 token（不确认；身份缓存条目按指纹键留着，无副作用）
前缀不合法       ⇒ 拒绝（既有行为）
resolveTokenIdentity(raw) 成功
                ⇒ rememberTokenIdentity(fp, id)  →  gmSet(githubPat, raw)
                   顺序不可颠倒：token 在存储里出现时，它的身份**已经在缓存里**
401             ⇒ 既有失效上报 + **拒绝保存**（token 已死，保存无意义）
其余失败          ⇒ **仍然保存**、身份留空、console.warn
                  （不得因为查不到身份就拒绝保存前缀合法的 token —— 身份查询已实测对两类凭证都可用，
                    走到这一支意味的是**临时性故障**（网络 / 5xx / 429），不是能力缺失；
                    拒绝保存会把一次网络抖动变成「用户存的 token 没了」）
```

由此：**id 与 token 的绑定发生在保存时，并以指纹为键持久化** —— 这正是「为什么不是把 id 与 token 绑定」
的答案：绑定就是那张指纹缓存，只是它此前**只在页面渲染时被动填充**（且组合 B 永不填充），本版把它
提前到保存路径上，于是 token 一旦存在，归属就是确定的。

### 3.3 读路径：同步解析（无异步、无网络）

```
getStorageUserId(): string
  tok = getToken()；fp = tok ? fingerprint(tok) : ''
  若 fp 与上次相同 ⇒ 返回上次结果        // 3 行快照，**不是绑定**，只是兜底
  id = (tok ? getTokenIdentitySync(tok)?.id : '') || getViewerId()   // 先 token 账号，再回退登录者
  记下 { fp, id }；返回 id（空串 ⇒ 调用方拒绝读写）
```

- **名字与签名不变** ⇒ `tags.ts` / `notes.ts` / `exportImport.ts` 的全部调用点零改动即跟随新口径。
- **不做会话级「冻结」**：绑定已在保存时完成（§3.2）。保留下来的只有**3 行快照**，它只在
  「保存时未能确认身份」（§3.2 的其余失败分支）这一种情况下起作用：防止网络恢复后同一个会话里
  键名从登录者翻转到 token 账号，导致刚写的标签读不到。快照按 token 指纹自失效，
  **不是**「记住 id」，也**不是**第二份绑定。
- **永不异步**：`getStorageUserId()` 被存储层**同步**调用（逐卡渲染路径），不得 await、不得顺手发请求
  （那会同时破坏 D26 的他人页零网络与 D25 的省额度口径）。
- **不回落裸键**：取不到归属 id 时标签 / 备注 / 宽限期一律读空、写 no-op（沿用现有护栏语义）。
- **组合 B 的永久缺口随之消失**：身份不再依赖「页面渲染时的求值」。

### 3.4 宽限期备份改为按键分区

- `constants.ts`：新增 `pendingDeletePrefix: 'stars_pending_delete_'`；**删除** `pendingDelete: 'stars_pending_delete'`
  （改后无任何读取者）。
- `storage/pendingDelete.ts`：加 `pendingDeleteKey()`；`loadPendingDelete()` → 归属 id 为空则 `{}`；
  `savePendingDelete()` → 归属 id 为空则 return + `console.warn`。
- 其余六个函数（`getPendingInGrace` / `listRestorable` / `markRepoUnstarred` / `markRepoStarred` /
  `addPendingFromImport` / `cleanupExpiredUnstarred`）**一行不改**（都经由上面两个存取函数）。
- **不加 owner 字段**：这张表的**行键就是 repoId**，两个账号对同一 repoId 各有一条备份时抢的是同一个位置 ——
  加 `owner` 字段不会多出一个位置，只是把「静默覆盖」变成「有标记地覆盖」。**分区（换个键）才是隔离**
  （与 `stars_tags_<id>` / `stars_notes_<id>` 同构）；分区之后「所属」由键名承载，再加字段就是同一事实的第二份拷贝。

### 3.5 披露：只改既有横幅，不加任何新 UI

1. **双方身份与差异**：`bannerMessage()` 两条分支**已经**同时点名 token 账号与网页登录账号
   （`src/ui/accountBanner.ts:91-120`），保留该形状并补一句归属说明
   「标签、备注与取消 star 后的宽限期备份属于 @&lt;tokenLogin&gt;」。
2. **按写通道分叉的措辞纪律不变**：classic ⇒ 「通常落 token 主人」+ 明确回落路径（REST 403 且存在会话时会走网页端点）；
   fine-grained / 无 classic ⇒ 落登录者。**不得**出现「读写永远同账号」这类断言（§2.1 末行）。
3. **任一侧变化即重弹**：关闭态键 `<tokenId>#<sessionId>` 已经做到这一点（任一侧 id 变化 ⇒ 键变 ⇒ 重新武装；
   两侧任一取不到 ⇒ 键为 null ⇒ 每次都弹）。本任务的活是**回归验证**它，并补上登录切换场景的**求值触发**
   （现有求值点只有三处：Token 保存成功 / 桌面转换成功 / `runFullSync` 的 finally —— 同标签页内换登录账号
   若不经这三处就不会重新求值；**只补触发，不加 UI**）。
4. **不做 chip、不做「不可关闭」**：AGENTS.md 风险 21 段原先要求「一处不可关闭的归属显示」，按用户
   2026-10-06 裁定改为**仅横幅**。代价明确记在 §7-1。

### 3.6 `stars_full_sync_meta.accountId`（只写不判）

- `types.ts`：`FullSyncMeta` 增 `accountId?: string`。
- `fullSync.ts:785-787`：整表同步成功落 meta 时写入当时的 `getStorageUserId()`。
- `hasApiData()` 与一切读门**不碰它**（避免 meta 缺字段就整页失去网格）。用途：归属显示 / 将来风险 14 的告警。

### 3.7 判据分工（写进文档，避免下次漂移）

| 面 | 判据 | 语义 |
|---|---|---|
| 数据面（标签 / 备注 / 宽限期备份的键） | `getStorageUserId() !== ''` | 「数据归属谁」（token 账号，回退登录者） |
| 成员关系 / 可编辑性面 | `getViewerId() !== ''`（`cardState.hasViewerIdentity` / `loadViewerCacheForView`） | 「浏览器里有登录会话吗」（存在性） |

两者都不做数值比较，故不产生新的错配。`cardState.ts` 的注释与 `DEVELOPER.md` 同步这一条。

## 4. 明确不做（边界）

1. **不新增任何 UI 节点**（无 chip、无提示条、不加按钮）；披露只在既有的 `.gsm-account-banner` 里做。
2. **不迁移任何旧数据**（V3）。正常情况 token 主人 == 登录者 ⇒ 两侧 id 相等 ⇒ 键不变、零影响；
   仅错号场景下旧的 `stars_tags_<登录者id>` / `notes` / 裸 `stars_pending_delete` 成为孤儿。
   一次性搬迁属 D30 已整批删除的那类代码。
3. **不动 `setStarState()` 的静默分派**（D3 / ADR 0006）：classic ⇒ token 主人；fine-grained / 无 classic ⇒ 登录者；
   classic 遇 403 permission-denied ⇒ 回落网页端点（登录者）。备份归属仍按**读路径**（token 账号）记录，与屏幕一致。
4. **不改 `exportImport.ts`**（见 §2 第 12 条）。
5. **不引入读路径上的异步请求、不改动同步关键路径、不在他人页发任何请求。**
6. **不做风险 14 的告警**（`accountId` 只写不用，见 §3.6）。
7. **不自动重试保存时的身份确认**，也不因此改变前缀校验行为。
8. **不因细粒度凭证引入 unknown 兜底分支**（已实测可用，见 §2.1/V7）。

## 7. 残留风险与已知取舍

1. **关闭横幅后，页面上再无任何归属痕迹**（用户裁定不加新 UI）：缓解 = 任一侧身份变化即重新武装；
   其余时间只有 console 与（将来）`full_sync_meta.accountId` 可查。这是本版**有意识放弃**的持续告知能力，
   AGENTS.md 风险 21 段原要求（「一处不可关闭的归属显示」）据此改写。
2. **指纹缓存是「曾经见过这份凭证」的缓存**，不是安全隔离手段：能读到 GM 存储的人可以改它 ⇒ 归属 id 可被伪造。
   调用方判定不得依赖它（现状也没有）。写进 `accountIdentity.ts` 的模块注释。
3. **保存时身份确认失败仍会保存 token**（§3.2）：此时归属回退登录者，且**只在本次会话内**被快照兜住；
   下次加载若确认成功，命名空间会切到 token 账号 ⇒ 该窗口内写的标签会「看起来消失」。
   取舍理由：拒绝保存会把一次网络抖动变成「token 没存上」，而身份查询能力本身对两类凭证都已实测可用（§2.1）。
4. **页面级 meta 无官方契约**：`octolytics-actor-id` 消失时，有 token 的用户**仍能**按 token 账号工作
   （这比现状更稳）；无 token 的用户读不到标签（与今天一致）。
5. **孤儿数据**（V3）：错号期写入的旧键数据不再被读取，但也不删除；换回匹配账号后可见。
6. **`stars_repo_cache` 仍不按账号分区**（风险 14 未解）：配错 token 时网格里的卡片集合仍可能是另一个账号的。
   本方案只保证「标签 / 备注 / 备份与列表同账号」，**卡片集合本身的归属**留待风险 14。
7. **每次 `getStorageUserId()` 多一次 `getToken()`（= 一次 GM_getValue）**：逐卡渲染路径下按卡片数线性增长
   （30 条约 30 次）。已知同类成本（他人页逐卡约 5 次 `GM_getValue`）已登记为待立项；本条同族，
   本轮不加读缓存（改动会波及全脚本共用的新鲜度语义）。
8. **细粒度 PAT 调 `GET /user` 无官方文档依据**（§2.1）：结论已由真机实测支持（可用），但它不在任何官方权限表里
   ⇒ 属**文档空白**的依赖，GitHub 有权收紧。届时表现为「该组合的归属退回登录者」（有 token 也可能按登录者分区），
   即「标签看起来没跟着 token 走」。不误报、不阻断，与 D25 同向降级；这是本方案唯一一处依赖未文档化行为的读路径。
