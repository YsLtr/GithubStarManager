## 0. 两个概念（本方案的固定交付物）

### 0.1 「备份」在这个项目里指什么

用户提问原话是「特别是 **备份** 在此是什么意思」。必须逐条钉死，否则整条风险都会被误读成「导出文件被覆盖」。

**它不是一个文件，不是导出包，也不是任何种类的副本文件。** 它是**同一份 TM（Tampermonkey）存储里的一个键里的一条条目**：

```
STORAGE_KEYS.pendingDelete = 'stars_pending_delete'
{
  "owner/repo": {
    ...仓库元数据（name / stars / lang / updatedAt …）,
    unstarredAt: 1730000000000,     // 进入宽限期的时刻（ms）
    _tags: ["我自己的标签"],          // ← 所谓「备份」的标签
    _note: "我自己的备注"             // ← 所谓「备份」的备注
  }
}
```

证据：`src/constants.ts:35`（键名）、`src/types.ts:27-31`（`PendingDeleteEntry extends RepoData` + 三个附加字段）。

| 时刻 | 发生什么 | 出处 |
|---|---|---|
| 取消 star 成功 | 把**活区**（`stars_tags_<账号id>` / `stars_notes_<账号id>`）里的标签/备注**抄进**这个条目，**随即清空活区**，并把整表缓存里的该条目删掉 | `src/storage/pendingDelete.ts:101-123`（清空活区 `:121-122`、缓存删除 `:116-119`） |
| 24h 内重新 star | 把 `_tags` / `_note` **抄回活区**，把条目写回 `stars_repo_cache`，删除 pending 条目 | `src/storage/pendingDelete.ts:125-141` |
| 超过 24h 仍未 re-star | `cleanupExpiredUnstarred()` 把条目连同 `_tags`/`_note` **永久删除**（ADR 0003：不留墓碑行） | `src/storage/pendingDelete.ts:144-155`；`GRACE_PERIOD = 24h` |

所以「备份」= **一份 24 小时有效的暂存，且它是此刻标签/备注的「唯一副本」**（活区已被清空）⇒ 任何覆盖它的写入都等于**数据丢失**，而不是「备份过期了而已」。

**术语纪律**（`CONTEXT.md` 已成文）：
- `导出包` 条目明确 _Avoid_: **备份** —— 导出包是搬运物，pending 条目是临时状态，两者不可混用这个词。
- `宽限期备份` 条目已写明「它是临时的，不属于可搬运的数据」「存量条目**无来源标记**」—— 后半句正是风险 21 的病根。

### 0.2 风险 21 的内容（**只解释**；用户已裁定留到下一轮实现）

**一句话**：`stars_pending_delete` 是整个存储里**唯一一个不按账号分片的键**，条目里**也不记录归属**；而读它的身份门只判「**有没有**登录者」，不判「**这条属于谁**」。

#### 归属口径（用户 2026-10-05 裁定）

**备份条目应有归属标记；标签/备注只跟 token 账号走**。切换账号会触发既有的 token 与登录账号不一致警告（D25），用户忽略该警告即视为已知晓「这些内容不属于此登录账号，而属于 token 所属账号」。

这条口径**修正了初稿的一处实质错误**：初稿把「归属 = 登录者」当既定前提（沿用 D27），按本口径应取 **token 账号** —— 因为**读路径（网格显示的是哪些 star）本来就是 token 账号的**：`src/fullSync.ts:196` 带 `Authorization: Bearer ${tok}` 打 `api.github.com/user/starred`。**展示与归属必须同一个账号**，否则屏幕上显示 A 的列表、标签却记在 B 名下 —— 那正是风险 21 的形状。

#### 与已发布决策的直接冲突（**必须改口径，不能只加字段**）

**D27（4.12.0）规定标签/备注的隔离账号 = 登录者**（`src/storage/tags.ts:18-19` → `pageScope.getViewerId()` → `octolytics-actor-id`；消费点 `src/storage/notes.ts:14,23`、`src/storage/exportImport.ts:58,152`）。本口径要求改为 **token 账号** ⇒ **D27 的定义要改写**。
- 正常情况（token 主人 == 登录者）两侧 id 数值相等 ⇒ 存储键不变、**零数据迁移**。
- 只在双账号错号场景键不同 —— 那正是本风险的目标场景。

#### 修复必须满足的四条

1. **归属 id 的来源**：token 账号 id 只能来自 D25 的 `GET /user`（异步），而 `getStorageUserId()` 被存储层**同步**调用（`tags.ts:30,37`、`notes.ts:14,23`、`exportImport.ts:58,152`）⇒ **不能在那里 await**。可行形态只有一种：复用**已存在**的指纹缓存 `STORAGE_KEYS.accountIdentity = { [token指纹]: { id, login } }`（`src/constants.ts:46-48`），按当前 token 指纹**同步查表**。**不得**改成「读取时顺手发一次身份请求」—— 那会破坏他人 stars 页的零网络硬约束（D26）与 D25 的省额度口径。
2. **必须键分区，不是加字段**：`PendingDeleteMap` 是 `Record<repoId, entry>`（`src/types.ts:36`），两个账号对**同一 repoId** 各有一条备份时会**互相顶掉**；加一个 `owner` 字段只是让顶掉「有标记地」发生。唯一可行形态是**键分区** `stars_pending_delete_<归属id>`（与 tags/notes 同构）。
3. **无 token / 登出的缺省**：无 token ⇒ 「读路径账号」退化为**登录会话**；无登录者身份 ⇒ 一个字符都不读（D26 不变，夹具 `other-logout-pending` 已钳合实证）。
4. **写通道的镜像错配要写清**：`setStarState` 在 classic 下写 token 主人、fine-grained / 无 token 下写**登录者**、classic 遇 403 还**回落网页端点**（`src/starWrites.ts:299-304`）⇒「有 fine-grained token 的用户 unstar」这次写落在登录者名下。本口径仍把该备份记在 **token 账号**下，代价由 D25 的横幅文案承担。

#### 两处「照字面实现会坏」与一处**永久性**缺口

- **「所属标记」照字面实现不能达成隔离** ⇒ 必须落成键分区。
- **「忽略警告 = 已知晓」在当前披露面上不成立**：D25 的横幅可被**永久关闭**（`stars_account_banner_dismissed = <tokenId>#<sessionId>`，同组合不再重弹，`src/constants.ts:49-51`）且只在本人页出现 ⇒ 错号是**持续状态**，「一次性知晓」承担不了持续告知。处置（与风险 21 同批）：① 横幅写明归属；② 增加一处**不可关闭**、在数据所在处可见的归属显示。
- **组合 B 的永久缺口**：`accountGuard.run()` 在 `!hasWebSession()` 时**直接返回 unknown 且完全不发身份请求**（`src/accountGuard.ts:154`）⇒ 该组合下指纹缓存**永不填充**，而 `getViewerId()` 有值（今天标签**读得到**）⇒ 若改成「只认 token、查不到读空」，这批用户的标签会**永久读不到**。默认降级见 V7。

#### 连带（与风险 21 同批）与范围

- 导出包身份随之改语义（`exportImport.ts:58,152` 同源 `getStorageUserId()`）⇒ **本方案正好在同一段代码上**，故 T1–T3 的改动必须与该口径**兼容**（不写死「登录者」）。
- 还差一个字段：决定「有哪些卡片」的是 `stars_repo_cache`，只给 pending 加归属仍答不了「这个网格是谁的列表」⇒ 完整修复**包含改 `stars_full_sync_meta`**（与既有风险 14 同源）。
- **D30 的告诫**：以上都靠「开发阶段 / 无已有用户」这一前提免掉迁移代码；前提一旦失效，依据立刻作废。

## 1. 风险 22 与修复路线的纠正

### 1.1 AGENTS.md 的既定处置（据此改路线）

> **顺带消除风险 22**：它的触发前提是「导入会往 `stars_repo_cache` 补条目 ⇒ 与宽限区条目并存」；新策略**不再写缓存** ⇒ 重叠不复存在，风险 22 应标为「已由导入导出策略变更消除」。 —— `AGENTS.md:33-34`

### 1.2 我前几轮方案错在哪（两处）

1. **位置错了**：改的是**破坏点**（`markRepoUnstarred` 覆盖语义）；AGENTS.md 的路线是**消除状态生产者**（导入写缓存）。重叠态的**唯一生产者就是导入写缓存** —— 正常 unstar 必删缓存条目（`pendingDelete.ts:116-119`）、同步分支 B 走 `markRepoStarred` 会删 pending（`fullSync.ts:716-728`）、`confirmExternalUnstar` 有 `if (!existed)` 门且同样删缓存（`starCheck.ts:105-119`）；只有 `applyImportPackage` 第 3 段会**只补空缺地**往缓存加条目（`exportImport.ts:219-228`）⇒ 导入一改，那条「空覆盖非空」分支**不可达**，为它写合并语义等于**写死代码**。
2. **撞上 AGENTS.md 已指出的歧义**：风险 22 原文写着「『空活区该覆盖还是该保留』本身是宽限期语义的选择（**空活区也可能是用户真的删光了标签，那时覆盖才对**）⇒ 需要自己的判据与验收」（`AGENTS.md:1095-1096`）。我前几轮直接判「空活区不表达用户意图」，在「用户真删光」那一支上是**错的**。消除前提后该歧义**整体消失**（状态不可达）—— 这正是 AGENTS.md 选这条路线的理由。

### 1.3 保留：那条原则仍然有效

「**不得用空值覆盖非空备份**」这条纪律**不随破坏点一起丢**：本轮新引入的宽限期写入者（导入分派）必须遵守它（§2.2 / V4），否则就是把同一个缺陷模式复制到新入口上。差别只是**修在新代码上，而不是修在即将不可达的旧分支上**。

## 2. 设计（三条可验收项，来自用户原话）

### 2.1 导出：不再携带仓库元数据

- `buildExportPackage()` 删掉 `keptCache` 段（`exportImport.ts:75-81`）与 `data.repoCache` 的构造（`:86`）⇒ 包只留 `tags` + `notes`（+ 协议元信息）。
- `ExportPackage.data.repoCache` 改为**可选**（旧包仍可能带）；`validateRepoCache` 保留，但只在字段**存在**时校验、**不再写入缓存**。
- 论据（落 ADR 0001 追加段）：带 repoCache 的**唯一收益**是「导入后立刻有完整卡片」；而本地没有的仓库现在进宽限期、**不建卡片**，新设备真正该做的是同步一次 —— 元数据本就由同步承载。
- `ImportReport.repoCacheAdded` 失去读者 ⇒ 删除。

### 2.2 导入：按「本地 star 确认」逐仓库分派

| 本地状态 | 去向 | 规则 |
|---|---|---|
| **确认已 star**（`hasApiData()` 且 `stars_repo_cache[repoId]` 存在） | **活区** | **沿用 D9**：标签并集（本地在前）、备注以包为准但**空备注不覆盖**本地非空备注 |
| **确认未 star**（有完整缓存、但该仓库不在缓存里） | **宽限期** | 新入口写入，带 `_tags` / `_note`（`unstarredAt = now`） |
| **无法确认**（`hasApiData()` 为假） | **先自动同步一次** | 见 §2.3；同步后仍不可用 ⇒ 一律按「未确认」进**宽限期** |
| 该仓库**已在宽限期** | 合并进已有条目 | 空不覆盖非空；**保留原 `unstarredAt`**（不续命） |

**新入口的两条纪律**（V4；**不得复用** `markRepoUnstarred`，它会删缓存、清活区，且无条件覆盖）：

1. **空不覆盖非空**：包内该仓库无标签 / 备注 trim 后为空 ⇒ 保留已有条目的 `_tags`/`_note`。
2. **合并而不重置**：目标已有条目 ⇒ 合并、保留原 `unstarredAt`（否则导入会给一条即将到期的备份「续命」）。

**写盘纪律沿用现状**：按仓库逐个写、只在有实际变化时落盘；纯逻辑层不碰 DOM（D9 的分层铁律）。

### 2.3 无缓存 ⇒ 自动同步一次（V2 改判；含失败语义）

```
读文件 → 校验 → hasApiData() 为假?
   ├─ 是 → await 一次全量同步（「确认本地 star 状态」的唯一手段）
   │        ├─ 成功 → 用刚拿到的缓存逐仓库分派（§2.2）
   │        └─ 失败（未配 token / 401 / 网络 / 完整性红线 / 被并发丢弃）→ 一律按「未确认」进宽限期
   └─ 否 → 直接用现有缓存分派（仍不自动同步 —— ADR 0005 的其余部分保持）
```

- **编排在 UI 层**（`ui/exportImportMenu.ts`）：D9 明写纯逻辑层**不触发同步**；D23 要求 **`runFullSync()` 的签名与五个调用点不变**（不可 await 则加极薄包装或订阅 `SyncState` 直到离开 running，不改它本身）。被并发丢弃的同步不算失败（D23：不广播 failed）⇒ 按「未能完成确认」走宽限期分支。
- **失败时不退回写活区**（这是本次改判的要点）：写活区会让「未确认」的仓库以**已 star** 的样子出现在网格里（网格来自缓存，而这些仓库根本不在缓存里 ⇒ 实际渲染不出来、也没有 UI 入口，等于静默丢弃）。进宽限期至少有 24h 窗口 + 恢复入口 + 同步发现已 star 时自动移出。
- **24h 必须写进提示**：同步失败/无缓存分支的文案要写死「请在 24 小时内完成一次同步，否则这些标签/备注将被删除」——宽限期超期即**永久删除**，不写就是静默删除承诺。

### 2.4 「下次同步成功发现已 star ⇒ 直接从宽限区移出」= **既有行为**，本轮只加断言

用户指令的这条**已经是实现**，无需新代码：`fullSync` 的**分支 B**（「远端有、本地无」）本就有

```ts
// src/fullSync.ts:716-728（现状）
if (pending[it.repoId]) {
  markRepoStarred(it.repoId);      // _tags/_note 抄回活区 + 条目写回 stars_repo_cache + 删 pending 条目
  saveRepoData(it.repoId, patch);  // 用**远端**元数据补齐
  restored += 1;
}
```

两个关键点：① `markRepoStarred()` 正是「移出宽限区」（数据回活区、条目进缓存、pending 条目删除，`pendingDelete.ts:125-141`）；② 紧跟的 `saveRepoData(patch)` 用远端的元数据补齐 —— 这点**很关键**，因为导入产生的 pending 条目**没有**元数据（导出包不再带 repoCache）。
副作用（可接受且对用户是有效信息）：这类恢复会计入同步简报的「恢复 N」。**本轮不写新代码，只在 T4 加一条断言 + T6 文档化。**

### 2.5 提示：写明「x 个仓库本地不存在」及其处置

- 确认框（`confirmText()`）说清破坏性范围（哪些会被覆盖）。
- 报告（`reportText()`）增加：**「x 个仓库本地不存在」**，其 tag/note 已放入宽限期 —— 同步或重新 star 后回到卡片。
- 同步失败 / 无缓存分支**必须写死 24h**：「请在 24 小时内完成一次同步，否则这些标签/备注将被删除」。
- 同步进行中要有可见状态（复用既有 SyncState / 通知栈，不新造 UI）。
- 不带实现术语（不出现「导出包字段 / 缓存」这类内部词）。

### 2.6 已知退化（接受）

导入产生的宽限期条目**没有仓库元数据**（包不再带 repoCache，且这些仓库本就不在本地缓存里）⇒ 恢复窗口里 `RestorableEntry.name` 回退成 `repoId`（`pendingDelete.ts:78-84` 的 `e.name || repoId`）。不为此保留 `repoCache`（那正是本轮要删的东西），等下一次同步成功由分支 B 的 `saveRepoData` 补齐（与 AGENTS.md 风险 17 ④「字段缺失即降级」同口径）。

## 6. 风险与残余

- **残余（本轮接受）**：风险 21 原样存在，下一轮按 V7 修；`markRepoUnstarred` / `confirmExternalUnstar` 的写入形态本轮**一字未动**（不动现在是有意的：路线改成了消除前提）。
- **残余（本轮新增，需明确披露）**：同步失败时标签/备注进入 **24h 倒计时**。缓解有三层：① 提示写死 24h 与补救动作；② 24h 内任意一次成功同步都会把**已 star** 的仓库自动移出宽限期（§2.4 的既有分支 B）；③ 恢复窗口始终可用（TM 菜单）。再往后超期即按设计永久删除。
- **残余**：导入的标签若落在「本人没 star」的仓库上，行为**变了** —— 从「留在活区、不渲染、无 UI 入口」（D31 末条 / 风险 20 记载的现状）变为「进宽限期 → 同步发现已 star 则移出，否则 24h 后删除」。**这是用户明确要的**，故 T3 的提示必须写清，且 D31 末条 / 风险 20 的措辞要同步更新，否则文档会与实现相反。
- **风险**：导入现在可能**阻塞数秒到数十秒**（等一次全量同步）⇒ 必须有可见状态与「失败也继续」的确定性路径；`runFullSync` 的并发丢弃（D23）要按「未能完成确认」处理，不能抛错中断导入。
- **不做**：新 ADR（改为追加 0001 / 0005）/ CHANGELOG / 存储键改名 / 卡片状态判定（D31 不动）/ 风险 21 的任何实现 / `markRepoUnstarred` 的覆盖语义。

### 8.1 🔴 首版「风险 22 已消除」的论证被推翻（两轮审查各自独立跑到同一结论）

**缺陷**：分派条件写成 `hasApiData() && cache[repoId]`，而 `hasApiData()` 读 `stars_full_sync_meta`
（`!lastFullSyncAt || count<=0 ⇒ false`），与「缓存里有没有这个仓库」是**两个可背离**的量：
`markRepoStarred()`（恢复窗口 / 他人页 re-star 的落点）**只写缓存、不写 meta**，于是
「缓存里已有该仓库、`hasApiData()` 仍为假」**可达** ⇒ **已在缓存里的仓库被判成「未确认」而进宽限期**
⇒「缓存条目 + 宽限期条目并存」复活 ⇒ 风险 22 原样回归。

**审查员的最小复现**（两步都是真实函数）：无 meta 导入 ⇒ `markRepoStarred` ⇒ 再导入 ⇒ **并存态 = true**；
继续走一遍「同步补上 meta → 卡片出现 → 点 unstar」⇒ `_tags: ['x']` 被**空活区**覆盖成 `[]`（数据丢失）。

**归谬教训（比结论更值钱）**：首版列了三条「收口路径」当作证据，它们**只覆盖正常流程**，漏掉「缓存与 meta
背离」这个**不被任何不变量守住**的状态。⇒ **证明「某状态不可达」必须穷举它的构造者，而不是列举已知流程。**
（同一条纪律本仓库已有前例：D29 的 P1「既有断言都是静态快照，缺陷只在点下去之后才显现」。）

**修法**：判据收敛为**缓存成员关系**（`if (!localCache[repoId])`）；`cacheAvailable` 降级为**纯展示标志**，
不参与分派。判据收敛后「不可能由导入产生」才真正成立。

**回归锁 + A/B**：`tests/exportImport/run.cjs` 新增 `[12]`（复现「缓存有、meta 缺」的背离态）。
A/B 反证：把判据改回带 `hasApiData()` 的形式 ⇒ `[12]` **4 条断言变红**（含「不产生并存态」那条直接打印出
pending 里多出来的条目）；还原后 88/0。

### 8.2 🟡 导入条目在恢复菜单里**永远恢复不了**（假承诺）

**缺陷**：导入产生的宽限期条目 `name` 缺省成**数字仓库 id**（导出包不带元数据、仓库也不在缓存里），
而 `restoreOne` 的守卫要求 `name` 含 `/` ⇒ 菜单给出的「☆ 恢复」按钮**点了必然报「仓库名缺失，无法恢复」**；
而 4.17.0 的确认框明确向用户承诺「重新 star…即自动恢复」—— 承诺无法兑现。
原计划把它记为「已知退化（接受）」，实际**低估**了：这不是观感退化，而是一个不可能成功的按钮。

**修法（⚠️ 已被用户裁定取代，见 §9）**：当时收敛到 `restore.ts` 的 `isRestorableName()`（唯一一处），
菜单对这类条目不显示勾选框与按钮、只显示「等同步恢复」。**这是 UI 层掩盖，且是未与用户讨论的行为改动** ——
用户裁定改为**在数据层修**（导出包随带最小标识 `data.repoNames`），该修法**已整体回退**
（`restore.ts` / `ui/restoreMenu.ts` 现与 HEAD 逐字一致）。当前口径见 §9。

### 8.3 🟡 只在 `notes` 出现的仓库会多写一次 `stars_tags_*`（本版引入的回归）

**缺陷**：`repoIds` 取 `tags ∪ notes`，而一个**只在 `notes` 里**出现的仓库带着 `incomingTags = []` 进入活区
分支，旧代码的 `if (merged.length > 0) saveTags(...)` 会**原样写回**本地标签。老实现按
`Object.keys(pkg.data.tags)` 遍历、根本不会进入标签循环 ⇒ 这里是**新引入**的一次多余落盘，
且与函数注释「只在有实际变化时落盘」自相矛盾。审查员实测：本地 `tags[r1]=['local']`、包
`{tags:{}, notes:{r1:…}}` ⇒ `GM_setValue` 里出现一次 `stars_tags_111`（旧实现 0 次）。
**修法**：改为「**只在真的有新增时**落盘」（`merged.length > before`）。

## 9. 用户裁定的修法（推翻 §8.2 的 UI 层处理）

**用户原话**：> 你擅自修改了代码，此处应与我讨论修复方案。应该在导出处修复，增加仓库名的最小导出和导入。

**两条指控都成立**：
1. **流程错**：§8.2 是方案选择（改行为），我未经讨论直接改了代码。
2. **方向错**：正确落点在**数据层**，不在 UI 层。UI 层「不显示按钮」是把入口藏起来，数据仍然不可恢复。

### 9.1 现在的实现（数据层）

| 项 | 内容 |
|---|---|
| 包格式 | `data.repoNames?: Record<repoId, "owner/repo">`（新增，**可选**）。值取自整表缓存的 `RepoData.name`（= GitHub `full_name`）；**查不到就不写这个键**（不编造） |
| `EXPORT_SCHEMA_VERSION` | **仍为 1** ⇒ 旧包照常导入（只是没名字），与 V5 一致 |
| 导入侧 | 名字**只**写进宽限期条目的 `name` 字段；**绝不写 `stars_repo_cache`**（否则风险 22 的触发前提就回来了，有专门断言钉住） |
| 合并纪律 | 与标签/备注同一条：**空不覆盖非空**（已有条目的 `name` 优先，包里的名字只用来补空） |
| 校验 | `repoNames` 缺省放行；存在则必须是「字符串 → 字符串」（非字符串 = 整包拒绝，与既有严格校验一致）。值里没有 `/` 属语义问题，在导入侧按「没有名字」降级，不为一个标签挡住真正的标签/备注 |
| **已回退** | `restore.ts` 与 `ui/restoreMenu.ts` 的 §8.2 改动**整体撤销**，两文件现与 HEAD 逐字一致（`git diff` 对它们为空）。恢复菜单回到原样：按钮照常显示；真遇到没名字的条目如实报「仓库名缺失，无法恢复」 |

**仍然不可手动恢复的两种情形**（降级，不是缺陷）：① 导出方本地也查不到该仓库的名字（有标签但从未 star）；
② 导入的是**旧包**（无 `repoNames`）。两者都会在下一次成功同步（`fullSync` 分支 B 的 `saveRepoData` 补齐
`name`）后变成可恢复。
