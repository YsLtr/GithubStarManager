# Token 归属校验（脚本 token 的账号 vs 浏览器当前登录账号）

当**同时**存在「脚本持有的 token」与「浏览器已登录的 github.com 会话」时，两者的账号**可以不是同一个**。4.10.0 及之前，脚本从不比对它们 —— 于是存在一条真实的错号路径：网格里的星标数据来自 token 主人的账号，而点星操作可能落到浏览器登录者名下，且**方向恰好相反**（显示「已 star」→ 点击发的是 unstar）。本 ADR 记录 4.11.0 补上这一环的判定口径与已接受的降级。

## 为什么两侧会不一致（问题陈述，非实现细节）

写路径是**静默分派**的（ADR 0006）：

| 凭证情况 | 写操作实际落到谁名下 |
|---|---|
| 有 classic / OAuth（`ghp_` / `gho_`）token | **token 主人**（REST `PUT`/`DELETE /user/starred/{o}/{r}`） |
| 无 classic token，或 REST 返回 fine-grained 的权限 403，且存在登录会话 | **浏览器登录者**（网页端点 `POST /{o}/{r}/star`，Cookie 会话认证） |

读路径（`GET /user/starred`）**永远**用 token。所以只要 token 与登录会话分属两个账号，读与写的目标账号就不同：

- fine-grained token 属 A + 浏览器登录 B ⇒ 数据来自 A、操作记到 B，方向相反；
- classic token 属 A + 浏览器登录 B ⇒ 读写在 A 上自洽，但脚本占位的是 **B 的 stars 页面**，用户看到的列表与页面上下文不符。
- 批量恢复（`restore.ts`）与卡片星按钮共用 `setStarState`，一并受影响。

## 已定案的行为

- **比对键是数字 `id`，不是 `login`**。两侧各取数字 ID：浏览器侧 **`meta[name="octolytics-actor-id"]`（登录者）**，token 侧 `GET /user` 响应的 `id`。**`login` 只用于文案**。依据：官方明文 `login` 可随时间改名、`id` 持久（<https://docs.github.com/en/rest/users/users>）；用 `login` 会在用户改名后产生**永久误报**，而长期常驻的误报比漏报更伤害这套 UI 的可信度。
- **浏览器侧必须取「登录者」而不是「页面主人」（第二轮审查 P1-2，实测）**。页面 meta 里有两套身份，语义不同：

  | 字段 | 自己的页 `/YsLtr?tab=stars` | 他人页 `/mattn?tab=stars` | 语义 |
  |---|---|---|---|
  | `user-login` | YsLtr | **YsLtr** | 登录者 login |
  | `octolytics-actor-id` / `-login` | 130123551 / YsLtr | **130123551 / YsLtr** | **登录者** id / login |
  | `octolytics-dimension-user_id` / `-login` | 130123551 / YsLtr | **10111 / mattn** | **页面主人** id / login |

  第一版误用了 `octolytics-dimension-user_id`（即既有的 `getStarsUserId()`），于是**打开任何他人的 stars 页**都会把页面主人当登录者 ⇒ 假阳性，横幅还会断言「浏览器登录的是 @mattn」并建议改用 mattn 的账号登录。取不到 `octolytics-actor-id` 时**不回退**到 `dimension-*`（回退等于恢复假阳性），一律判 `unknown`。证据：`.diag/probe-viewer-id.js`（登录态真机只读同源 fetch）。
- **只在「有 token + 有登录会话 + 两侧数字 ID 都取到」时判定**。其余组合一律不判定：
  - 有 token、无登录会话 ⇒ 写路径只有 REST、账号由 token 唯一决定，无错号风险；
  - 无 token ⇒ 本期不判定（见「已知局限」第 2 条）。
- **取不到身份 = 不判定（`unknown`），既不冒充「相符」也不误报「不符」**。`GET /user` 返回 401 时**不**走归属告警，而是走既有的 token 失效上报链（`notifyTokenIssue` → 配置横幅）—— 失效与归属不符是两件事。
- **不阻断写路径**。检测到不符时只显示警告横幅，卡片星按钮与批量恢复照常工作。理由：网页端点通道是 fine-grained 用户获得写能力的唯一现实手段（ADR 0006），且用户可能是**刻意**让 token 与浏览器登录分属两个账号（如个人号读、工作号写）。是否处置交给用户。
- **警告 UI**：`div.gsm-account-banner`，与配置横幅**同一落位规则**（复用 `placeSetupBanner` 的 Lists 槽位 / 网格列顶分流），**但不复用 `.gsm-setup-banner` 类名** —— 那个类名出现在 4 条撤除路径上（横幅内联保存后、Token 保存回调、同步成功后、`viewTeardown` 第 3 项），而复用会让归属警告在「保存了新 token」「同步成功」时被静默删掉且再无重建时机。横幅 `role="alert"`，只给两个控件：打开既有 Token 配置面板、关闭（原设计的 classic 创建页深链按钮经用户裁定移除：配置面板里本就有同款深链，且同时给出 fine-grained 深链与粘贴行）。
- **关闭态持久化** = `stars_account_banner_dismissed` = `<tokenId>#<sessionId>`：同一对账号不再打扰（重开页面也不弹），**组合一变立刻重新武装**。该键属页面级偏好，不随视口回滚。
- **求值点**，且都 fire-and-forget、不得进入 `runFullSync` 的关键路径或影响 `SyncState`：桌面转换成功出口、Token 保存成功后、
  **Token 清空时**、`runFullSync` 的 `finally`（同步链上唯一全覆盖点）。**4.18.0 追加第五处** `visibilitychange`
  （账号可能在本标签页之外被换掉；三道门见 `DEVELOPER.md` §6）—— 本条原文写「只有三处」，已被后续两轮扩充。
- **窄视口完全惰性**：求值首行判视口，窄视口直接返回 `unknown`（不建节点、不发请求）。横幅样式位于 `base.css` 的媒体查询之外，靠 JS 门守（同 D18）。跨断点变宽时由既有 `transformAndReveal(false)` 重新求值。
- **沿用「不向用户披露通道」**（ADR 0006 的同一条裁定）：横幅文案只讲**后果**（数据取自谁、操作记到谁、两边会不一致）与两条可执行出路（换匹配的 Token / 改用 token 所属账号登录），**不出现**「网页端点 / 浏览器登录会话 / GitHub-Verified-Fetch / REST」等实现词。

## 依据

- **`GET /user` 对 fine-grained PAT 不需要任何权限**：官方端点页原文「The fine-grained token does not require any permissions.」 <https://docs.github.com/en/rest/users/users>。classic 侧原文「A token without scopes still authenticates as the token's owner」—— 即两类已支持凭证都拿得到身份，不存在权限缺口。
- **官方汇总页漏列该端点**：`endpoints-available-for-fine-grained-personal-access-tokens` 的 users 章节**没有** `GET /user`。经反例交叉验证，该页**只收录「需要至少一项权限」的端点**（需 `Metadata` read 的 repo events 被收录；声明免权限的端点一律不收录）⇒ 漏列与「是否可用」无关，以逐端点参考页为准。（注：该汇总页源文件头部标 `autogenerated: github-apps`。）
- **额度成本**：`GET /user` 在 primary 限流下按**请求数**计 1（官方「1 点/5 点」表属 secondary 限流，不作用于 primary；与本仓库既有实测 D1 独立吻合）。指纹缓存命中后稳态零请求。
- **页面 meta 无官方契约（本方案最大不确定性）**：`meta[name="user-login"]` / `octolytics-dimension-*` 均非官方接口 —— `octolytics-*` 是 GitHub 自家埋点（有 GitHub 员工 2013 年的公开说明：<https://github.com/pengwynn/pingwynn/issues/6>），`user-login` 被 GitHub 前端用于跨标签页登录态检测。**反面证据**：`<meta name="csrf-token">` 曾是惯例，如今在 github.com 上**已完全消失** —— meta 会无预告变更，这不是理论风险。
- **同类实现（事实参照）**：refined-github 的 `github-token.ts` / `api.tsx` 已在做同构比对（token 的 `GET /user` `.login` vs `getLoggedInUser()`，不一致即抛 `Your token belongs to "X" but you are logged in as "Y"`），其登录用户取自 `github-url-detection` v11.2.4 的 `meta[name="user-login"]`。差别：它是在**多个候选 token 里挑一个匹配的**（它要给任意 GitHub 页面找可用 token），本脚本只有单一 token，故只告警、**不自动切换凭证**（自动换 token 会悄悄改变数据来源账号，是更危险的静默行为）。
- **不存在「用浏览器会话查当前账号」的官方 API**：官方认证文档只描述 token 凭据，且明确不支持用户名密码；从已登录页面带凭据 `fetch` `api.github.com` 被 CORS 拦死（服务端 `ACAO: *` 且无 `ACAC`）。故「浏览器侧身份」只能取自 DOM meta。
- 完整查证报告（逐条含 URL、原文引用与证据强度）：`.pi/tmp/research-token-identity.md`（gitignore 目录，可重新生成）。

## 已知局限（知情接受）

1. **页面身份 meta 无契约**：若 `octolytics-actor-id` / `user-login` 被移除或改名，本功能**静默失效**（判 `unknown`，
   不弹任何东西），脚本其余行为不变 —— 这是**有意的降级方向**：实现要求是「失效 = 退回今天的行为」，不是「失效 = 满屏误报」。
   注意**不得**为此回退到 `octolytics-dimension-user_id` —— 那是页面主人，回退等于恢复假阳性（见上第 4 条）。
2. **「无 token + 有登录会话」组合不告警**：该组合下网格缓存可能来自上一个账号，要先有账号归属字段才能可靠告警，属独立改动
   （记在 AGENTS.md 已知风险）。**4.18.0 更新**：字段**已加**（`stars_full_sync_meta.accountId`，**只写不判**），
   现有读门与告警行为不变；做那条告警时才读它。
3. **GHES / SAML SSO 下 meta 行为未确证**：GitHub Docs 全站（含各 GHES 版本）、`github/docs` 抽查、相关 issue 与 userscript 社群均无权威来源。若用户群含 GHES，本功能可能完全失效（仍为 `unknown`，不误报）。
4. **多标签页不同步**：一个标签换了 token，另一个标签的关闭态与身份缓存不即时同步（与既有「TM 菜单标签不跨标签同步」同源）。
5. **不符时仍允许写**（有意）：代价是「用户知道有风险仍可能误操作」，由横幅文案把后果写清来缓解。
## 发布前独立审查修复（4.11.0 内已落地）

**第一轮**：外部 reviewer 只读复核整批 diff（自建复现实验，抓到 2 个 P1 + 3 个 P2，**全部已修**）：

1. **P1 · 异步返回后没有复判 ⇒ 收窄视口后残留可关闭横幅**（违反 D18）。求值只在**进入时**判一次视口，
   `.then` 里建节点时不再判 —— 慢网下 `GET /user` 在途期间把窗口拖到 <768px（teardown 已跑完），
   延迟返回的 mismatch 会在手机上**重新建出** `role="alert"` 的完整样式横幅（横幅 CSS 在 `@media` 之外，
   真的会显示），且再没有任何东西会撤掉它。修：`mountAccountGuard` 捕获 `currentGeneration()`，
   resolve 后**世代复判 + 视口复判**（缺一不可 —— 世代挡「这一轮已过去」，视口门挡「窄视口不该有 UI」）。
   实测：在途收窄 → teardown 后 banner 0 / grid 0 / `gsm-*` 节点 0 → 释放请求（延迟 resolve）后**仍为 0**；
   拖回桌面则横幅正常重现。
2. **P1 · 文案无条件断言「加星会记到浏览器登录账号」，classic 场景下是错的**。写路径静默分派：
   classic / OAuth 凭证走 REST、落到 **token 主人**，此时「加星会记到登录者」不成立，会把用户
   引向无收益的换号操作 —— 而误报正是本功能最要避免的东西。修：`AccountVerdict` 新增 `writeTarget`
   （`isClassicCredential(token)` 决定），文案按通道分叉。

   **同轮复审推翻了我自己第一版的修法**（用户质询后重新实测）：第一版把 classic 分支写成
   「**都会**记到 @tokenowner（**不会**改动 @session）」，这同样是过度断言 —— 写通道是**按次**决定的：
   `setStarState` 在 REST 返回 **403（非限速）且存在登录会话**时会回落网页端点（`src/starWrites.ts:299`），
   那一次写就落到登录者名下。实测证据（`.diag/assert-account-fallback.js`，跑真代码、非手搓请求）：

   ```
   DELETE https://api.github.com/user/starred/owner3/repo3   → 403 非限速
   POST   /owner3/repo3/unstar                               → 回落网页端点 ⇒ 落到 @smoke-user
   fellBackToWebEndpoint = true
   ```

   ⇒ 最终措辞：classic 分支说「**通常**也记到 @A（不会改动 @B）……**若 @A 的 Token 被 GitHub 拒绝，
   操作会改以 @B 的身份进行**」；fine-grained 分支落点是确定的（有会话时只走网页端点、失败**不**跨通道回落），
   故仍可直说「会记录到 @B」。**只有 fine-grained / 无 classic 那条路才允许做确定性断言。**
3. **P1 · 清空 Token 后过期警告不撤**（第一轮 P2 的修复在**真实路径**上不成立）。`hasToken` 链路本身正确，
   但三个求值点**都覆盖不到「清空 Token」**：不进转换、不进 `setTokenSavedHandler`，而 `runFullSync` 的无 token
   早退发生在 `try` **之前**（故 `finally` 不执行）—— 于是「Token 属于 @A」会与「🔑 Token 已清除」并存。
   修：`index.ts` 的 `setTokenIssueHandler` 内一并 `mountAccountGuard()`（清空走的正是 `notifyTokenIssue` 这条链）。
   实测（走真实 TM 菜单入口 + 真实 `promptForToken`，prompt 返回空）：`pat=""` 且归属横幅 **0**。
4. **P1 · 非本人 Stars 页假阳性 + 把页面主人说成登录者**（`octolytics-dimension-user_id` 是**被访问者**）。
   见上方「比对键」一节的实测表：改用 `octolytics-actor-id`（登录者），**取不到时不回退**。
   实测：他人页 + token 属 42（≠ 登录者 999）⇒ 弹且说 @smoke-user；他人页 + token 属 999 ⇒ **不弹**。
5. **P2 · 关闭后换回旧组合，屏上残留另一对的横幅**：`showAccountBanner` 的 `isDismissed` 早退前补 `removeExisting()`。
   实测：「42#999 → 关闭 → 77#999 → 回到 42」不再残留 77 的横幅。
3. **P2 · 清空 token 后横幅不撤**：「确定没有 token」与「取不到身份」原本合并成同一个 `unknown`，
   而 `unknown` 口径是「不得抹掉警告」，于是清 token 后过期的归属警告会与配置面板并存。修：
   `AccountVerdict` 新增 `hasToken`，`mountAccountGuard` 在 `match` 或「`unknown` 且 `!hasToken`」时撤节点；
   其余 `unknown`（含判定异常，保守取 `hasToken: true`）仍什么都不做。实测：清空 token + 重新求值 ⇒ banner 0。
4. **P2 · 未接入 `setHideListsRepositionHandler`**：横幅与配置横幅走同一套落位规则，却不跟随「隐藏 Lists」
   开关重挂，关掉开关后横幅会紧贴冒出来的原生 Lists 上方。修：新增 `repositionAccountBanner()` 并在
   该 handler 里一并调用。实测：切换后 banner 仍为 1。
5. **P2 · `AccountMatch` 是零消费者 export**（与 D21「删多余 export」口径相抵）：已改回模块内类型。

**第二轮**：另一位 reviewer 复核修复后的状态（端到端实测），再抓到 2 个 P1 + 1 个 P2，**全部已修**（见上第 3/4/5 条 —— 其中「清空 Token」与「身份字段语义」两条都说明：**第一轮的修复在真实触发链上不成立**，只测「重新求值后是否正确」会漏掉「产品从不重新求值」）。

## 被否决的备选

- **用 `login` 比对**：改名即永久误报，且唯一出路是让用户重配 token —— 否决。
- **每次写操作前校验**：每次写多 1 次 primary 请求，且会把「身份不符」混进写路径的失败语义（ADR 0006 划定的失败文案口径），使「静默分派」变成「静默失败」—— 否决；只防**结构性错号**（配置层面就不一致）。
- **周期性轮询身份**：meta 变化本身没有事件，轮询纯耗额度（对照：窄视口进页自动同步的 2s 定时器都因「纯耗额度」被门掉）—— 否决。
- **阻断写路径**：见「已定案的行为」—— 否决。
- **复用 `.gsm-setup-banner` 类名**：会被 4 条既有撤除路径静默删掉 —— 否决。
- **内联 token 输入框**：配置横幅已有一整套填 token UI 与保存链，复制一份 = 两个保存状态机、两套文案 —— 否决；横幅改为指向既有配置面板。
