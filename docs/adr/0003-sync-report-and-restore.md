# 变化简报与恢复

一次全量同步的结果（取消 star / 新增 / 恢复的条目）必须可见并可操作：同步收尾后弹出**变化简报**（右上角 Notification Stack 样式，新条目从底部追加、不设上限、3s 自动消失、鼠标悬停整个区域时暂停计时），简报里对「取消 star」条目提供**恢复**按钮，每行之后另有一个 **star 按钮**可直接单条恢复；手动取消 star 同样弹一条带恢复按钮的通知；TM 菜单提供全量恢复窗口（可勾选 + 一键「恢复选中」+ 每行 star 按钮）。理由：这是脚本里唯一可能造成**数据丢失**的事件（宽限期备份 24 小时后永久删除标签与备注），此前它只写进控制台日志，用户对数据风险完全无感。

## 已定案的行为

- **简报触发**：任何 `runFullSync` 路径（手动 / 进页自动 / token 保存后）都在**同步收尾后**弹，无变化也弹「无变化（共 N 个 star）」；自动同步受既有 60s 冷却约束。导入链路**不再自动同步**（见 `0005-no-auto-sync-after-import.md`）。**不判重**：每次同步各弹一条（相同摘要意味着中间必有变化，重复显示才诚实）。
- **简报口径**：取消 star / 新增 / 恢复三者计数，元数据刷新不计入。取消 star 含「同步检测到的外部取关」与「用户手动取消」两类，**不标注来源**。
- **恢复 = 真实远端写请求**：REST `PUT /user/starred/{owner}/{repo}` 返回 204，**或**网页端点 `POST /{owner}/{repo}/star` 返回 200 并事后重读页面 `form` 方向确认（见 `0006-web-endpoint-write-fallback.md`），才 `markRepoStarred()`。**禁止只做本地回滚**——那会制造「本地有星、远端无星」的状态，下一轮同步又会把它判成外部取关。
- **失败分支**：一律只 `alert` 一行文字（无 token / 401 / 403 / 404 / 超时），**不隐藏恢复按钮、不代替用户判断状态**。404 不恢复本地、条目留在宽限期。
- **队列**：卡片星按钮与恢复共用**全局串行队列**，变异请求间隔 ≥1s（官方 best-practices 的 serial/queue 与 pause-between-mutative 两条要求，两件事：串行是硬要求、1s 是建议间隔）；卡片仍乐观翻转。**排队中的请求可被再次点击撤销**（用户改主意时不必等它发出）；恢复按钮在排队期间 `disabled`，避免同一仓库重复入队。恢复窗口**由脚本代发**（非「引导用户点原生按钮」，见 `0006`）：一键「恢复选中」+ 每行 star 按钮，`confirm` 显示条数与预估耗时，窗口内逐条显示进度（`n/N ✓ owner/repo`），失败继续、结束时汇总，**执行中可取消**（取消只停后续，已发出的不回滚），**不自动重试**，**不设数量阈值**（串行 + 1s 间隔已在官方建议范围内）。
- **UI 语义**：手动取消 star 的通知用「撤销」（用户刚做的动作）；同步简报用「恢复」（用户没做过这个动作，且新增没有对称动作）。恢复成功后原地划掉改为「✓ owner/repo 已恢复」并移除按钮，重置 3s 后消失；同一仓库在队列中恒最多一条，再次操作直接移除旧条目再追加新条目。
- **边界**：详情页不检测 star/unstar（该 todo 作废），详情页只显示简报、恢复后不触碰 GitHub 拥有的 star 按钮 DOM。
- **通道不披露**：写操作走 REST 还是网页端点的**静默分派对用户不可见**，UI 不出现通道实现细节；失败文案保持结果导向。**静默分派 ≠ 静默失败**：任何失败都必须报错（见 `0006`）。
- **不做**：批量端点不存在（官方 REST/GraphQL 均只接受单个仓库），故只能逐个请求。

## Considered Options

- **只做本地回滚（不回远端）**：被否决。见上「恢复 = 真实远端写操作」。
- **自动恢复检测到的外部取关**：被否决。无法区分「误操作」与「用户在别处故意取关」，且 D3 已知局限下私有仓库可能被误判为取关，自动恢复会与用户的真实意图对抗。
- **「恢复全部」保留但设在宽限期外仍可恢复**：被否决。24h 是既有 `GRACE_PERIOD`，超期即删除标签/备注；给已丢弃数据的条目留墓碑行会让用户以为仍可恢复。
