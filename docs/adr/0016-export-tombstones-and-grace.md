# 0016 · 导出包带墓碑与宽限期：让「网格上看不到的仓库」也能跨设备

- 状态：已采纳（4.23.0，2026-10-27）
- 相关：`0001`（导出格式）、`0003`（宽限期与恢复）、`0005`（导入不同步）、`0015`（墓碑）、`src/storage/exportImport.ts`、`src/storage/pendingDelete.ts`

## 背景

`0015` 之后，「卸载 star」这件事有三条去向，而导出包（`0001` / 4.17.0 修订）只覆盖第一条：

| 状态 | 数据在哪 | 旧导出包 |
|---|---|---|
| 正常 star | 活区标签/备注 + `stars_repo_cache` | ✅ `tags` / `notes` / `repoNames` |
| 墓碑（仓库已不可访问） | 活区标签/备注 + `stars_repo_cache` + `tombstone` | 标签备注 ✅，**元数据与墓碑标记 ✗** |
| 宽限期（24h 内取消 star） | `stars_pending_delete_*` 的 `_tags` / `_note`（活区已清空） | **全 ✗** |

这两类恰好**没有任何别的重建路径**：墓碑的定义就是「不在远端星标列表里」，宽限期条目同理 ——
同步永远拉不回来。旧包里它们等于凭空消失：墓碑退化成一张普通卡片（描述/语言/star 数全丢），
宽限期条目的标签与备注则**直接蒸发且没有任何提示**。

## 决策

导出包新增两段**可选**载荷，`schemaVersion` 仍为 1（只是多了可选字段，旧包与旧解析器都不受影响）；
两段都**只在非空时写入**，因此「没有墓碑也没有宽限期」的包形状与 4.22.0 完全一致。

```jsonc
"tombstones": { "<repoId>": { name, desc, lang, stars, forks, updatedAt, starredAt, private, fork, isTemplate, mirror, at, status } },
"grace":      { "<repoId>": { name, tags, note, unstarredAt } }
```

- **墓碑**：带足以复现卡片的字段（名称/描述/语言/star/fork/两个时间/四个 Type 标志）+ 判定本身（`at` / `status`）。
  标签与备注**不重复带** —— 它们在活区，已经在 `tags` / `notes` 里。
- **宽限期**：带 `_tags` / `_note` 与**原始 `unstarredAt`**。剩余时间原样搬过去，不续命。
  已超期条目**不导出**（按 `0003` 本来就当已删除）。

导入分派（顺序不可换：墓碑 → 宽限期 → 标签/备注主循环）：

1. **墓碑**：本地缓存**已有**该仓库 ⇒ 跳过（本地权威 —— 可能已 re-star 或已重新同步，不拿旧快照覆盖）；
   没有 ⇒ 建条目并写 `tombstone`。随后主循环看到「条目已在缓存里」，把标签/备注写进**活区** ⇒ 灰卡完整复现。
2. **宽限期**：本地已 star（缓存在） ⇒ 标签/备注**直接写活区**（要求的「已为 star 则直接应用」）；
   否则 `restorePendingFromExport()` 按包里的 `unstarredAt` 重建；**已超时 ⇒ 丢弃**。
   与既有导入共用三条纪律：空不覆盖非空、非空整体替换、不续命（与已有活条目合并时取**较早**的 `unstarredAt`）。
3. 同一 `repoId` 同时出现在 `grace` 段与 `tags`/`notes` 段时以**宽限期段为准**（主循环跳过它），
   避免同一仓库被两套规则各写一次。

写活区的规则抽成 `applyToActive()` 一份实现：普通分派与「宽限期但本地已 star」都走它 ——
风险 23 的成因正是同一条胜负规则存在两份实现。

## 已知代价 / 边界

- **包会变大**：墓碑段带完整元数据。只影响有墓碑的包（一般个位数条目），且是一次性文件。
- **跨账号仍被拒**：`user.id` 校验不变（`0001`），两段不改变归属语义。
- **宽限期条目跨机器后可能立刻过期**：这是「保留原始 `unstarredAt`」的必然结果，也是要求的行为
  （否则一次「导出→隔天导入」就能让本该死亡的备份重新活 24h）。
- 墓碑段不校验 `desc`/`stars` 的语义正确性，只校验类型；包里写什么就是什么（包是用户自己的文件）。
- 导入**已 star** 的宽限期仓库时不做 `git ls` 之类的可达性探测：判断依据只有「本地整表缓存里有没有它」
  （与 `0001` 的分派判据同一条），因此「本地缓存陈旧（其实已 unstar）」时会把标签写进活区 ——
  下一次同步按正常规则收口（远端无 ⇒ 进宽限期），数据不会丢。

## 验证

`pnpm test:exportimport` 组 `[17]`（30 条断言）：两段导出内容与筛选（超期不进包）、空机器导入重建、
本地已有条目不覆盖、超时丢弃、本地已 star 直接写活区、两段类型错误整包拒绝。
