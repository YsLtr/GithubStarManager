# 仓库请求目标以 ID 为主，名称作端点适配（D34）

状态：已实施，4.19.0。用户要求统一仓库/用户 API 寻址，授权依据调查计划修改代码。调查与取证见 [计划](../plans/2026-10-06-id-first-api-targets.md) 和 [端点实测](../research-api-targets.md)。

仓库写入、恢复、单条星标核对完整传递 repoId，执行时按 ID 解析当前名称。GET `/repositories/{id}` 在 classic 公共/私有样本上有效，GitHub 的历史名称路由也会重定向到它；但当前 OpenAPI 未收录它，属于实测能力。数字星标候选 `/user/starred/{id}` 的 GET/PUT/DELETE 实测均 404，所以正式星标请求继续使用官方名称端点，不在产品中探测该失败候选。

## 边界与代价

- 纯目标校验在 `api/repoTarget.ts`，网络解析/星标核对在 `api/repositories.ts`。存储、DOM 投影复用纯校验，不获得联网能力。非法 ID 与缺 ID 分开：名称投影键只在入口转换，数字 ID 已知时不能被名称替代。
- ID 404 可查名称，但最终响应 id 必须仍等于目标 ID；名称复用导致 ID 不同即失败。401、限流、网络错误不通过名称盲目重试。解析 404 不等于取关。
- 本来走 Cookie 的操作可优先用当前原生行的“同数字 ID + 标题地址 + 精确方向表单”确认目标，包含接管后隐藏的原生行；没有这种证据才查 API。classic 元数据权限/不可见失败也只在有同 ID 原生表单时回落 Cookie。没有 API 可见性且没有原生证据的私有离页目标明确失败，不拿缓存旧名直接写。
- 数据归属、写凭证和目标仓库是三个不同问题。D33 的 token 账号/登录者分工保持；GET `/user`、GET `/user/starred` 继续表示当前凭证主体，不替换为用户名或已缓存账号 ID。
- 队列 key 与展示 label 分离；等待和执行期都按 ID 去重，名称入口取得 ID 后再次认领，同批队列已完成的别名也会被拦。元数据解析只发生在执行期，取消排队不发请求。每次实际变异（含 REST→网页降级）都经过 1000ms 间隔门。
- 混合扫描先完成全部单仓库核对，再提交本地 diff；预算按每条最多三次显式读取预留，响应余量继续约束。全 304 和全正文扫描不增加逐仓库解析。已确认的当前名称同步刷新到缓存/恢复条目。
- 恢复支持 ID-only，远端成功后才还原本地数据。`repoNames` 仍是可选字段、schema v1 不变，现为名称提示；不再是手动恢复必备条件。导入逻辑不联网、不写仓库缓存。批量恢复遇到限流/凭证失效停止后续，其他单条失败继续。
- 元数据 GET 使用原生 Fetch follow（浏览器 manual 是不可读的 opaqueredirect），采用浏览器重定向上限、跨源剥离 Authorization，并检查最终 API origin/id。变异请求 `redirect:error`，目标中途改名时失败，不盲目追随写跳转。

通常一次操作多一次元数据 GET；无 token 的 API 读取受匿名额度约束。原生 DOM 本身可能过期，名称解析与写入之间也存在改名竞态，本实现不是原子 ID 写入保证。fine-grained 已补验本方授权私有仓库的无浏览器会话 REST 分支（ID 解析、双向写入、基线恢复均通过，见本轮计划）；真实 Cookie 私有目标和 TM 沙箱/CSP 的最终端到端行为尚未确证，不能用 mock 或 classic 成功代替。

历史裁决的调整：D32 的导入覆盖/分派不变，“缺 repoNames 无法恢复”由本决策替代；D10 的串行/取消/间隔保留并收紧到真实变异起点；D33 的账号归属不变。未增加存储迁移或风险 14 的账号缓存分区。

## 子代理审查修订（2026-10-06）

三名审查员分别检查覆盖、回退和稳定性，首轮发现并修复：非法非空 ID 被入口抹掉而退成名称；名称键恢复未统一数字落键；元数据超时只覆盖响应头；mock 断言可能被产品 catch 吞掉；旧网页方向检查把共存表单误作状态变化。

名称键恢复先解析数字 ID，写前检查数字目标的缓存、标签、备注、备份是否占用，以及源名称活区是否有数据；写后再次检查。冲突保留备份，不猜测合并；远端已成功而本地冲突时明确告知两者状态。成功时缓存/标签/备注统一写数字键，删除源名称备份。这是当前操作的目标规范化，不是历史存储迁移；数字 ID 入口仍沿用既有恢复行为，不能把名称路径的占用检查宣称为所有恢复的事务保证。

元数据读取的 20 秒 deadline 覆盖响应头与所需正文，结束时取消未消费正文。明确的 429 / retry-after 等限流信号在响应头阶段即失败；普通 403 读取正文识别 secondary rate limit。401 和限流放弃整个混合核对；普通资源权限 403 或网络失败只保留该项，其他已确认项可以提交。超时不会触发名称盲目重试。

网页写入仅以 HTTP 成功为证据；本页原生 star/unstar 表单同时存在，且 fetch 不会更新它们，已删掉无效方向复核。既有变异请求尚未加显式 deadline，仍可能长时间占用串行队列；本次超时修复不覆盖这项既有局限。
