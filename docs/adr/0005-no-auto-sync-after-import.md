# 导入后不自动同步


> ⚠️ **本页正文为 4.9.0 原貌，其中「导入后不自动同步」这一绝对口径已被 4.17.0 部分推翻**：
> 现在**只有一种情形**会同步 —— 本机还没有完整整表缓存时，导入**前**先自动同步一次。
> 另外正文里「导入包的 `repoCache` 条目先落本地缓存」在 4.17.0 起**不再成立**（导出包不再带仓库元数据、
> 导入也不再写缓存）。**当前口径以文末「4.17.0 修订」段为准**；正文保留原文以便追溯决策当时的状态。
导入完成后**不再**自动触发全量同步（推翻 `0001-export-import-format.md` 的「导入完成后直接调用同步函数」）。导入是数据搬运，落盘即完成；是否拉取远端由用户自己决定（标题行 Sync / TM 菜单）。导入本身仍会被完整同步流程正确处理：导入包里的 `repoCache` 条目先落本地缓存，若远端并不存在该 star，下一次同步的整表 diff 会把它判为本地独有，走既有的「外部取关 → 宽限期备份」管线（切片混合模式下先逐条 `GET /user/starred/{o}/{r}` 核对后才确认）。

## Considered Options

- **导入后自动 `runFullSync('button')`**（原决策）：被否决。导入结果已由 `alert` 摘要表达，再叠一条同步简报会让用户分不清两组数字；且导入的条目缺 `starredAt`（`buildLocalSlices` 的阀门 A）→ 立刻触发一次**无条件整表**拉取，对用户是意外的大请求。
- **保留自动同步但静音简报**：被否决。等于用一个不可见的写操作换用户的既定期望，比显式不同步更难解释。

## 4.17.0 修订：口径收窄为「需要确认本地 star 状态时才同步一次」

原文「导入后不自动同步」**被部分推翻**：现在只有一种情形会同步 —— 本机**还没有完整整表缓存**
（`hasApiData()` 为假）。原因是导入改为按「**本地是否确认已 star**」逐仓库分派（见 `0001` 的 4.17.0 修订）：
没有缓存就无从确认，而那些无法确认的仓库会被放进 **24h 宽限期**（超期即永久删除）。

- **有缓存时仍然不自动同步**：本页原文的理由（导入是数据搬运、落盘即完成）继续成立。触发条件用的是「本机有没有整表缓存」（`hasApiData()`），而**分派**判据是「该仓库在不在缓存里」—— 前者是后者的**保守超集**（`hasApiData()` 与「缓存里有没有这个仓库」是两个可背离的量，见 `0001` 的审查修正段）。
  这正是「无缓存才同步」这条口径的代价：**少数情况下会多同步一次**（缓存非空但某仓库缺失，其实不同步也能正确地把它放进宽限期），代价只是一次可能白发的请求；反过来若判据取严，就会漏掉「整表缓存为空、但用户其实已 star」的绝大多数情形。**取保守方向是有意的。**
- **同步失败不阻断导入**：未配 token / 401 / 网络 / 完整性红线 / 被并发丢弃（D23 不广播 failed）⇒ 未能确认的仓库一律进宽限期；提示里**写死**「请在 24 小时内完成一次同步，否则这些标签/备注会被删除」。
- **恢复路径是既有的**：24h 内任意一次成功同步发现「远端已 star」⇒ `fullSync` 分支 B 调
  `markRepoStarred()` 把标签/备注抄回活区、条目写回整表缓存、删除 pending 条目 ⇒ 自动移出宽限期。
- **编排在 UI 层**（`ui/exportImportMenu.ts`）：`storage/exportImport.ts` 是纯逻辑层，按 D9 的分层铁律**不触发同步**；
  `runFullSync()` 的**签名**未改（D23），但**新增了一个调用点**（导入前的这次同步）—— D23 原文的「五个调用点保持不变」
  因此需要按「签名不变、允许为新增流程再加入口」来读；同步状态的单一真相（`SyncState` / 头部按钮）不受影响。

**注意**：本页原文提到的「导入包的 `repoCache` 条目先落本地缓存」在 4.17.0 起**不再成立**（导入不写缓存）——
那一段的结论（远端没有该 star 时走既有外部取关管线）不受影响，因为宽限期条目同样由整表 diff 与分支 B 处理。
