# 导出包格式与导入合并语义

> **4.19.0 后续修订**：[ADR 0011](0011-id-first-api-targets.md) 已使数字 ID 可独立解析恢复目标。
> 下文“缺 repoNames 就不能恢复”的限制已被替代；schema v1、导入覆盖/分派与纯存储分层保持。

> **4.17.0 修订（两处，务必都读）**：
> ① `data.repoCache` **已从导出包移除**，导入也**不再写入 `stars_repo_cache`**，且导入改为按「该仓库在不在本地整表缓存里」逐仓库分派（不在的进 24h 宽限期）；
> ② 随后**又加回一个最小字段 `data.repoNames`**（每个仓库的 `owner/repo`）—— 它不是被移除的那种**描述性**元数据，
> 而是「恢复」这个写请求的**目标地址**（没有它，导入产生的宽限期条目无法手动恢复）；
> ③ 标签合并**由「取并集」改为「覆盖」**（用户 2026-10-05 裁定）⇒ 本页正文各处写的「标签取并集（本地已有在前）」
> 与 Considered Options 里那条「并集 + 备注单向覆盖」**均已作废**，当前规则见文末「第三处修订」。
> 本页正文描述的是 4.7.0–4.16.x 的形态；完整修订见文末「## 4.17.0 修订」。

导出包是**单个 JSON**，顶层 `{ kind, schemaVersion: 1, exportedAt, user: { id }, data: { tags, notes, repoCache } }`；**不含 `github_pat`**（敏感键，跨设备搬运 token 高危且无必要），**不含同步元数据**（ETag 基线），**不含宽限期备份**（临时状态，搬运即近乎立刻过期）。

`repoCache` 只带**有标签或有备注**的仓库——仓库元数据随时可由一次同步刷新，导出只需保证这些仓库在导入后立刻有完整卡片。

导入按 `kind` + `schemaVersion` 严格校验，不匹配则整包拒绝、不写任何键——沿用 DEVELOPER.md §6 的完整性红线精神。

合并语义：标签取并集（去重、本地已有在前）；备注以导入文件为准，**但空备注不得覆盖有内容的备注**——「空」的判据是 **trim 后为空**，`storage/notes.ts` 的 `saveNote` 判空同步收紧为同一判据（只输入空格/换行的备注视为删除）。

导出包带 `user.id`，只允许导入到同一用户 ID 下；当前页取不到 `user.id`（未登录 / GitHub 改版）时导出与导入**一律拒绝并提示**，不降级到无隔离的旧键——那会把数据写进一个「下次登录后读不到」的键，等于静默丢数据。

注意：`repoCache` 条目沿用「按 repoId 键」的结构，**不含命名空间**，因此 `user.id` 是导出包的自声明归属，不是数据隔离手段——身份校验必须在导入侧显式执行。

## Considered Options

- **导出仅标签/备注，不带仓库元数据**：被否决。在新设备导入后卡片缺仓库名/语言/star 数，等于必须再等一次全量同步才可用；代价只是一段 JSON，故为**有标签或有备注**的仓库带上 `repoCache`。
- **导出带同步元数据（ETag 基线 `etags` / `tailEtag`）**：被否决。ETag 基线与「当前 token 身份 + 远端瞬时状态」绑定，跨设备/跨时间导入会让「全 304 = 无变化」误判为「本地缓存即现值」，是数据正确性红线。
- **导出 `repoCache` 全部条目（含与当前 star 集合无关的脏条目）**：被否决。导出取最小集，脏条目对导入方无用。
- **允许跨账号导入**：被否决。repoId 是「我的 star 集合」的一部分，把别处数据挂到当前账号无法解释；`user.id` 不匹配即拒绝。
- **导入时弹「覆盖 / 合并」二选一**：被否决。多一套对话框与状态机；并集 + 备注单向覆盖已能表达用户的主动意图。
- **导入前自动导出一份当前状态**：被否决。会连续触发两次下载（浏览器可能拦截后一次），且无法保证用户真的保存了文件。
- **`GM_download` 之外再挂 Blob + `<a download>` 原生兜底**：被否决。TM 的扩展名白名单是**用户设定的安全边界**，原生下载能绕过它，等于让脚本替用户推翻自己的设置；而且 TM 因白名单/功能未开拒绝时**不抛错、只走 `onerror`**（TM 文档：`GM_download` 返回 `{ abort }`，只有 `GM.download` 才是 promise），同步 try/catch 根本捕获不到，所谓兜底在它唯一有意义的场景里是**死代码**。故只调 `GM_download`：不可用或同步抛错就返回失败并提示，白名单类失败由用户去 TM 设置解决。

## Consequences

导出的 JSON 与账户绑定，天然不可作为跨账号迁移工具；若将来确需迁移，得先把标签键改成不按用户隔离，那是另一个决策。

导入是破坏性操作（备注可能被覆盖）且**不做自动备份**：回退只能靠用户自己事先导出的文件，提示写在导入 `confirm()` 文案里。

## 交互与流程

导入的破坏性动作由**原生确认对话框**承载（`window.confirm`），校验失败用 `window.alert` 报原因且**不弹确认**——校验失败时不存在可执行的操作，同一种对话框会让用户以为「点确定就能强行导入」。与 `starCheck.ts` 的 `window.prompt` 同族；脚本只运行在 github.com（`@match https://github.com/*`），不引入页面内确认条。

导入完成后**不自动同步**（原「直接调用 `runFullSync('button')`」已被 `0005-no-auto-sync-after-import.md` 推翻）：数据落盘即完成，是否拉取远端由用户自行决定。导入包的 `repoCache` 条目若在远端并不存在，会在下一次同步的整表 diff 里被判为本地独有，走既有的外部取关管线。

导入**不触发导航**：TM 菜单在仓库详情页/纯 profile 页也能点，导入后数据已落盘，用户下次进 Stars 页自然会读到新数据；重新渲染只在「Stars 页且网格已存在」时执行。

文件名 `<script-slug>-<user.id>-<YYYY-MM-DD-HHmm>.json`（本地时区、分钟精度，不含 Windows 禁用字符）；包内 `exportedAt` 写 ISO 8601 UTC——文件名给人看，字段给程序看。`<script-slug>` 必须**单源**，脚本改名时文件名跟着变，但包内 `kind` 是协议身份、**永不随改名变动**。

导出时清洗：trim 后为空的备注**不写入导出包**，其余备注文本**原样保留不 trim**（避免吃掉用户在备注里有意写的前导空格）。`storage/notes.ts` 的 `saveNote` 判空同步收紧为「trim 后为空」，只影响写入——存量空白备注不做批量清洗（无渲染危害，不值得为显示瑕疵做全体用户写操作）。

## 4.17.0 修订：导出包不再带仓库元数据，导入按「本地 star 确认」分派

**改了什么**

- 导出包 `data` 只剩 `tags` + `notes` + **最小标识 `repoNames`**（`repoCache` 字段被删除；字段类型在源码里转为**可选**以兼容旧包）。
- 导入**不再往 `stars_repo_cache` 写任何条目**；改为**逐仓库分派**：
  - 本地**确认已 star**（判据 = **该仓库在 `stars_repo_cache` 里**；~~`hasApiData()`~~ 见下方审查修正段，那半个是错的）⇒ 写**活区**（胜负规则见文末「第三处修订」：**包内非空即覆盖**，不再是本页正文写的「取并集」）；
  - 本地**确认未 star**（有缓存但里面没有该仓库）⇒ 进 **24h 宽限期**（`stars_pending_delete_<归属id>`，带 `_tags` / `_note`；
    键名 **4.18.0 起按归属账号分区**，此前是无分区单键 —— 见 `0010`）；
  - 本地**无法确认**（还没完整同步过）⇒ 导入前**先自动同步一次**，同步仍失败（未配 token / 401 / 网络 / 完整性红线）则与「确认未 star」同处置：进宽限期。见 `0005` 的 4.17.0 修订。
- `EXPORT_SCHEMA_VERSION` **仍为 1**：旧包（带 `repoCache`）**仍可导入** —— 字段照旧被校验，但内容**一律忽略**。

**为什么推翻「不带仓库元数据」（本页 Considered Options 第一条）**

原文的理由是「新设备导入后卡片缺仓库名/语言/star 数，等于必须再等一次全量同步才可用」。4.17.0 的新论据：
带 `repoCache` 的**唯一收益**就是「导入后立刻有完整卡片」；而**本地没有的仓库现在进宽限期、不建卡片**，
所以这个收益只对「本地已有 star」的仓库成立 —— 而那些仓库本来就在本地整表缓存里，不缺元数据。
新设备真正该做的是**同步一次**：元数据本就由同步承载，不该由导出包背。（唯一随包带回去的是**最小标识**
`data.repoNames` —— 它不是展示数据，而是「恢复」这个写请求的目标地址，缺了它恢复入口就不可用；
见下面第二处修订。`RestorableEntry.name` 因此不必回退成数字 id。）

**风险 22 因此被消除（而不是被修补）**

风险 22 的触发前提是「导入往 `stars_repo_cache` 补条目 ⇒ 与宽限期条目并存、活区为空」。
4.17.0 起导入不再写缓存 ⇒ 该并存态**不可能由导入产生** ⇒ `markRepoUnstarred()` 的「用空活区覆盖非空
备份」那条分支不再可达 —— 该函数 4.17.0 一行未动。
**纪律没有丢**：新引入的宽限期写入者 `addPendingFromImport()` 必须遵守「空不覆盖非空」与
「合并而不重置 `unstarredAt`」（否则就是把同一个缺陷模式复制到新入口上）。

**⚠️ 发布前独立审查推翻了本段的首版论证（同日修订，务必连这段一起读）**：首版只说「导入不写缓存」，
而分派条件写成 `hasApiData() && cache[repoId]` —— **多出来的那半个 `hasApiData()` 是错的**。
`hasApiData()` 读 `stars_full_sync_meta`，而 `markRepoStarred()`（恢复窗口与「他人页 re-star」的落点）
**只写缓存、不写 meta** ⇒「缓存里已有该仓库、`hasApiData()` 仍为假」是**可达状态**：此时**已在缓存里的
仓库会被判成「未确认」而进宽限期**，并存态与风险 22 一起复活（审查员用最小复现跑出并存态，并进一步
跑出「导入来的标签被空活区覆盖删除」的数据丢失）。
⇒ 修正：**分派判据收敛为缓存成员关系**（`if (!localCache[repoId])`），`cacheAvailable` 降级为**纯展示标志**。
归谬教训（比结论更值得记）：本段首版列的那三条「收口路径」是**不充分的证据** —— 它们只覆盖「正常流程」，
漏了「缓存与 meta 背离」这个**不被任何不变量守住**的状态。**要证明「某状态不可达」，必须先穷举它的
构造者，而不是列举已知流程。** 回归锁 = `tests/exportImport/run.cjs` 的 `[12]`（A/B 已验证：把判据改回
带 `hasApiData()` 的形式，该组 4 条断言立刻变红）。

**`data.repoNames`：为什么又放了一点仓库标识回去（4.17.0 第二处修订，用户裁定）**

移除 `repoCache` 之后暴露了一个真实缺陷（发布前独立审查抓到）：导入产生的宽限期条目**没有 `owner/repo`**
⇒ `RestorableEntry.name` 回退成**数字仓库 id** ⇒ 而手动恢复要往 `POST /user/starred/{owner}/{repo}` 发请求，
`restoreOne` 的守卫要求 `name` 含 `/` ⇒ 恢复菜单上的「☆ 恢复」按钮**点了必然报「仓库名缺失，无法恢复」**：
一个不可能成功的按钮，而导入确认框还向用户承诺了「重新 star 即恢复」。

**修法（用户裁定：修在数据层，不在 UI 层）**：导出包随带 `data.repoNames: { [repoId]: "owner/repo" }`，
导入时写进宽限期条目的 `name`。所以「不携带仓库元数据」这条**收窄为**：不携带**描述性**元数据
（语言 / star 数 / 描述 / star 时间），但携带每个仓库的**最小标识**。这不是撤回上一节的决定 ——
上一节反对的是「拿导出包当卡片的元数据来源」；`owner/repo` 不是展示数据，它是**恢复写请求的目标地址**，
缺了它那一侧的入口根本不可用。

三条边界（都有断言钉住）：

- **值取自本地整表缓存**（`RepoData.name` = GitHub 的 `full_name`），**查不到就不写这个键** —— 不编造；
  导入侧绝不拿它去填 `stars_repo_cache`（那会把上面「风险 22 因消除前提而消除」的论证再推翻一次）。
- **空不覆盖非空**：已有条目的 `name` 优先，包里的名字只用来**补空**。
- **仍然是可选字段**，`EXPORT_SCHEMA_VERSION` 维持 **1** ⇒ 旧包照常导入，只是没名字。

**仍然不可手动恢复的两种情形**（降级，不是缺陷）：导出方本地也查不到名字（有标签但从未 star）、
导入的是**旧包**。两者都如实报「仓库名缺失」，并在下一次成功同步（`fullSync` 分支 B 的 `saveRepoData`
补齐 `name`）后恢复可手动恢复。

**曾在审查轮走过的弯路**：一度改在恢复菜单里「不显示按钮」并把判定抽成 `restore.ts` 的 `isRestorableName()`
—— 那是**UI 层掩盖**、且是未与用户讨论的行为改动。用户裁定改为在数据层修后，`restore.ts` 与
`ui/restoreMenu.ts` 的改动**已整体回退**（两文件现与 HEAD 逐字一致）。

## 4.17.0 第三处修订：标签合并由「取并集」改为「覆盖」（用户裁定）

**用户原话**：> 取并集不在我的决策中，应该改成覆盖

「标签取并集（去重、本地已有在前）」是本页 4.7.0 的原决策，不是用户定的。改为**覆盖**后的完整规则
（也见 `CONTEXT.md` 的「导入覆盖规则」）：

> **去向按「该仓库在不在本地整表缓存里」分派；胜负规则两边相同：包内该字段非空 ⇒ 覆盖目标；
> 为空 / 缺省 ⇒ 保留目标。**（「空」= trim 后为空）

于是 4.17.0 引入的那处**不对称消失**（当时活区取并集、宽限期覆盖 —— 曾登记为风险 23，现已消解）。

**为什么「空」保留而不是清空**（这条不是宽容，是必须）：一个仓库可能**只出现在 `notes` 里**
（它有备注但没标签）⇒ `incomingTags` 是空的。若把「空」当成「清空本地标签」的指令，就等于
「导入一份没说它标签的文件，结果它的标签没了」。备注同理。

**被本处修订推翻的**（原文保留，仅供追溯）：

- 本页正文「合并语义：标签取并集（去重、本地已有在前）」段 —— **作废**，现在是覆盖。
- Considered Options 的「**导入时弹「覆盖 / 合并」二选一**：被否决。…并集 + 备注单向覆盖已能表达
  用户的主动意图」—— 该理由随之失效（不再有「并集」这边），但**结论仍然成立**：不引入二选一对话框，
  规则统一为覆盖（用户也没要求可选项）。
- 本页 4.17.0 小节里「写活区（沿用本页的并集 / 空备注不覆盖语义）」—— 前半句作废。

**代价（明确接受）**：导入一份**较旧**的包会把你**之后在本地新加**的标签覆盖掉（活区不再并集）。
这正是「导入的内容更新、理应覆盖」的直接含义；缓解手段是确认框里已写明「会覆盖这些仓库本地的标签与备注」，
且完成提示会报出「其中被替换掉的本地标签 N 条」。**导入前不会自动备份**（本页原有口径不变）。

**已知的次要偏差**：仓库只出现在 `notes`、或包内标签归一化后为空数组时，**标签这一侧**既不计 `tagsWritten`
也不计 `tagsRemoved`（备注仍按 `notes` 正常处理）；进宽限期的仓库不计入 `notesApplied`、也不计入 `notesSkippedEmpty`（4.16.x 会计）；它们只由 `pendingAdded` 体现。
都只影响提示文案。**归一化**（去重 + 剔空白项）只在循环开头做一次、两条去向共用 —— 故 `['']` 与 `['x','x']`
分别是「空」与 `['x']`。
