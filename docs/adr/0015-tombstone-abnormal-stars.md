# 0015 · 墓碑：把「仓库消失」与「手动取消 star」分开

- 状态：已采纳（4.22.0，2026-10-27）
- 相关：`0011`（ID 寻址）、`0003`（恢复与宽限期）、`src/fullSync.ts`、`src/storage/tombstone.ts`、`src/ui/cards.ts`、`src/ui/restoreMenu.ts`
- 触发：<https://github.com/YsLtr/GithubStarManager/issues/5>「再检测仓库状态判断 unstar 原因」

## 背景

整表同步发现「本地缓存有、远端星标列表没有」时，旧实现一律当成**用户手动取消 star**：把条目搬进 24h 宽限期、清空活区标签/备注。可是同一个现象还有另一种成因 —— **仓库本身已消失或不可访问**（删除、DMCA 下线、改私有且 token 无权读取）。两种情况的用户动作完全不同：

- 手动取消 star：用户是主动的，可能后悔 → 24h 恢复期是对的；
- 仓库异常：用户没有做任何事，仓库已经回不来 → 恢复按钮没有意义，但元数据、标签、备注不该跟着消失。

## 决策

同步对每个「远端列表里消失」的缓存条目先探测仓库本身是否可达，再决定去向：

| 探测结果 | 判定 | 去向 |
|---|---|---|
| 仓库可达（200） | 手动取消 star | 既有 `applyExternalUnstar` → 24h 宽限期 |
| 404 / 410 / 451 | 仓库异常 | 留在整表缓存并打 `tombstone: { at, status }`，卡片变灰 |
| 网络 / 限流 / 401 / 403 | 证据不足 | 本轮不动（不搬数据、不写墓碑） |

- 全正文整表模式只需**存在性**核对（星标成员关系已由整表证明），比切片模式少一发 `/user/starred`。
- 已在墓碑上的条目**不重复探测**：它本来就不在远端列表里，每轮都发请求只是浪费额度。
- 仓库重新出现在星标列表（re-star 或恢复公开）⇒ 交集分支清墓碑，灰卡变回正常卡。
- 墓碑卡片的标签/备注仍在**活区**（不是宽限期备份），所以照常可编辑、可筛选、随导出包走；
  `stars_repo_cache` 本来就是 GM 存储（并镜像到 localStorage），元数据不因墓碑而删除。
- 对墓碑卡片再点一次 unstar：**不发写请求**（必然 404），直接走 `markRepoUnstarred` → 24h 宽限期；
  搬进备份时剔除 `tombstone` 字段，恢复后不会继续是灰的。
- TM 菜单窗口改为「取消 / 异常的 Star 仓库」两个分区：已取消的可单条/批量恢复；
  异常的只能删除（单条或「删除全部异常」），删除会连同标签与备注一起清掉（否则是无入口的孤儿数据）。

## 已知代价 / 边界

- classic token 无 `repo` scope 时，私有仓库的探测也是 404 → 会落成墓碑而不是「取消 star」。
  这是有意选的降级方向：墓碑保住了元数据与标签，且仓库恢复可访问后自动清墓碑（旧的误判会直接清标签）。
- 403 不当作「不可访问」：它无法与权限/限流区分，宁可不判定。
- 全正文模式下每个嫌疑条目新增 1–2 次请求；额度余量不足时整轮同步放弃（与切片核对的既有红线一致），不会带着半份判断落盘。
- 删除墓碑是**不可撤销**的本地删除，UI 明确提示（含标签/备注）。

## 验证

- `tests/api/run.cjs`：墓碑生成（404 保留缓存/标签、不进宽限期）、可达仓库仍走普通 unstar、
  已墓碑不重复探测、仓库回归清墓碑、墓碑批量删除连带标签/备注。
- 静态：`pnpm check` 绿（`@grant` 仍恰 5 项）。
